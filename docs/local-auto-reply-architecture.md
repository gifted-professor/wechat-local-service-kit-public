# 本地微信自动回复链路说明

这份文档是给第一次接触本项目的人看的，目标是说明三件事：

- 这套“读微信消息并自动回复”的链路到底是怎么工作的
- 本地项目、微信 App、模型 API 各自负责什么
- 微信 App 更新后，这套方案哪些地方可能失效、该怎么维护

当前结论先放前面：

- 当前方案不是“云端直接调微信 API”
- 当前方案是“本地读库 + 受监督的本地 UI 发消息”
- 开发环境不是运行时依赖；真正需要的是本地服务和微信本体在线
- 如果要给别人用，最终形态更适合做成“本地代理程序 + 模型 API”

## 1. 方案总览

这套方案的核心思路是：

1. 从本地微信数据库读取聊天记录
2. 识别某个会话是否有新消息
3. 把新消息和历史上下文整理出来
4. 由固定规则或模型 API 生成回复
5. 在人工确认后，再通过本机微信 App 的 UI 自动化把回复发出去
6. 最后反向读取数据库，确认消息确实已经写入

一句话概括：

`收消息走数据库，发消息走受监督的微信 UI`

这是当前个人微信场景里最现实、也最稳的一条路线。

## 2. 为什么不是直接调用微信 API

个人微信并没有给普通开发者一套稳定、合规、通用的官方消息收发 API。
所以这个项目不能像企业微信或客服系统那样，直接在云端调一个 HTTP 接口完成收发。

因此我们现在采用的是本地方案：

- 读：直接读微信本地数据库
- 发：在人工确认后，驱动本机微信窗口完成搜索、粘贴、发送

这也是为什么项目必须运行在登录了微信的本地 Mac 上，而不是纯云服务器上。

## 3. 当前链路由哪些部分组成

### 3.1 原版微信 App

原版微信负责：

- 保持账号在线
- 同步新消息到本地数据库
- 真正把自动回复发出去

注意：

- 原版微信必须保持登录
- 可以在后台运行，但不能完全退出
- 如果微信退出、掉线、电脑睡眠太久，本地数据库就不会继续刷新

### 3.2 测试版 / 调试版微信 App

调试版微信只在“抓 key / Frida 调试”时临时使用。

它的作用是：

- 去掉 Hardened Runtime 限制
- 让 Frida 能顺利 `spawn + attach`
- 抓到 `CCKeyDerivationPBKDF` 产生的 PBKDF2 日志

不建议长期使用调试版作为生产收发客户端，因为：

- 它只是重签副本
- 不适合当长期主力微信
- 微信更新后通常要重新复制和重签

### 3.3 本地项目脚本

本地项目脚本才是真正的自动化核心。

它负责：

- 解密 `contact/session/message_*.db`
- 解析联系人、会话、消息
- 监听某个会话是否出现新增消息
- 在人工确认后，驱动微信 UI 搜索会话并发送文本
- 反向验证消息是否写入本地库

当前仓库里与自动回复主线最相关的脚本：

- `scripts/grab_wechat_key.py`
- `scripts/match_wechat_key.py`
- `scripts/chat_crypto.py`
- `scripts/parse_chat_history.py`
- `scripts/watch_conversation_messages.py`
- `scripts/wechat_ui_send.py`
- `scripts/auto_reply_once.py`

### 3.4 模型 API

模型 API 可以接在这套链路中间，负责“生成回复内容”。

典型职责包括：

- 意图识别
- 消息分类
- 历史上下文总结
- 自动生成回复文案
- 风险判断和是否需要人工接管

所以 API 可以替代的是“大脑”，而不是“手和眼”。

不能被 API 替代的部分是：

- 本地读取微信数据库
- 本地操控微信 UI 发送消息

## 4. 一条完整自动回复链路长什么样

下面是一条完整的端到端流程：

### 阶段 A：初始化

1. 给本地环境开好 Frida 调试权限
2. 用调试版微信抓 PBKDF2 日志
3. 得到 `/tmp/wechat_frida_keys.log`
4. 后续按每个 DB 的 salt 自动匹配解密 key

这一步不是每次都要做，但通常在下面这些情况下需要重来：

- 微信更新后
- 更换账号后
- 重新复制了调试版微信
- 原来的 Frida key 日志不再可用

### 阶段 B：读取消息

1. 原版微信保持后台在线
2. 本地服务定时轮询 `message_*.db`
3. 把有变化的消息库解到临时可读副本
4. 对目标会话做增量读取
5. 找到最新的新消息

当前仓库已经验证过：

- 原版微信后台运行时，本地聊天库会持续更新
- 可以在不打开调试版微信的情况下抓到新增消息

### 阶段 C：生成回复

这一层有两种模式：

- 固定回复模式：收到新消息后发固定文案
- API 模式：把新消息和历史上下文交给模型 API，返回回复内容

目前仓库里已经完成的是固定回复闭环验证。
真正产品化时，建议把这一层切换成 API。

### 阶段 D：发送回复

发送走的是微信 UI 自动化，而不是数据库写入。

当前策略是：

1. 激活微信
2. 聚焦左上角搜索框
3. 输入会话候选词
4. 回车进入目标会话
5. 粘贴消息
6. 回车发送

推荐使用的搜索候选词优先级：

1. 备注名
2. 显示名
3. 昵称
4. alias

内部真正稳定的会话主键是 `conversation_username`，但 UI 搜索更适合用备注名或昵称。

### 阶段 E：发送验证

发送成功不能只靠“osascript 没报错”来判断。
更稳的是：

1. 发送后等待数据库刷新
2. 再次读取该会话最新消息
3. 用回复文本做精确匹配
4. 确认回复已写入数据库

当前仓库已经完成这一步的 PoC 验证。生产化前仍应保留人工确认、日志和异常回退。

## 5. 目前已经验证通过的能力

基于当前仓库状态，已经跑通的能力包括：

- 抓取聊天库 key
- 导出完整聊天记录
- 监听单个会话的新消息
- 在原版微信后台运行的情况下持续读到新增消息
- 通过微信 UI 给指定联系人发送固定文本的受监督 PoC
- 受监督回复一轮并验证写库的 PoC
- 多轮监听和回复循环的基础逻辑已经具备

也就是说，这已经不是纸面架构，而是已有真实闭环的本地自动化链路。

## 6. 如果要给别人用，推荐什么形态

如果只是自己用，当前仓库脚本加本地运行就够了。

如果要给别人用，更推荐做成下面这个形态：

### 6.1 本地代理程序

在用户自己的 Mac 上跑一个本地服务，负责：

- 读取微信本地数据库
- 监听新消息
- 调用模型 API 生成回复
- 控制微信 UI 发送

可以是：

- Python 常驻进程
- Node.js 本地守护程序
- 菜单栏应用
- 小型桌面客户端

### 6.2 API 负责智能部分

API 更适合承接：

- 回复生成
- 对话记忆整理
- 话术模板管理
- 是否自动回复的判断
- 风险审核

### 6.3 不建议的形态

不建议把它理解成“纯云端微信机器人”，因为：

- 个人微信没有稳定官方 API
- 收发仍依赖本地已登录微信
- UI 自动化也必须发生在本地设备上

所以更准确的产品方向应该是：

`本地代理 + 远程模型 API`

而不是：

`纯云端 API 机器人`

## 7. 微信更新后会不会失效

会，有概率，而且这是这类方案必须正视的现实问题。

但不是“每次一更新就全部失效”，而是以下几个层面可能受影响。

### 7.1 最容易受影响：抓 key 阶段

风险来源：

- 微信签名和 Hardened Runtime 变化
- Frida attach 策略变化
- `CCKeyDerivationPBKDF` 的调用路径变化
- 调试版副本需要重新复制和重签

症状通常是：

- `grab_wechat_key.py` 抓不到日志
- `PermissionDeniedError`
- `/tmp/wechat_frida_keys.log` 为空

维护方式：

- 重新复制并重签调试版微信
- 重新跑 Frida preflight
- 必要时更新 hook 逻辑

### 7.2 容易受影响：数据库结构

风险来源：

- `contact/session/message_*.db` 表结构变化
- 列名变化
- 具体消息表命名规则变化
- `is_sender`、`status` 等字段语义变化

症状通常是：

- 导出消息数异常
- 消息方向判断不准
- 某些消息类型解析错乱
- 自动回复验证逻辑失真

维护方式：

- 更新 `parse_chat_history.py`
- 更新消息方向和字段映射规则
- 增加针对新结构的兼容逻辑

### 7.3 容易受影响：微信 UI 自动化

风险来源：

- 搜索框焦点行为变化
- 快捷键响应变化
- 聊天窗口结构调整
- 辅助功能树变化

症状通常是：

- 搜索失败
- 发到错误会话
- 文本没粘贴进输入框
- 看起来执行了但实际没发出

维护方式：

- 调整 AppleScript / 辅助功能动作
- 增加截图确认
- 增加顶部会话名校验

### 7.4 相对稳定：模型 API 部分

这一层通常不容易因为微信更新而失效。
它的主要变化来自：

- 模型升级
- API 参数变化
- 提示词调整

所以整个系统里，真正最脆弱的是“微信本地实现细节”，不是“API”。

## 8. 怎么降低更新带来的维护成本

建议把系统拆成几层，每层单独维护：

### 层 1：解密层

负责：

- 读取 salt
- 自动匹配 Frida log
- 产出可读 SQLite 副本

受影响时，只修解密脚本，不动上层。

### 层 2：解析层

负责：

- 联系人解析
- 会话解析
- 消息方向和消息类型解析

受影响时，只修字段和表结构适配。

### 层 3：决策层

负责：

- 判断是不是要回复
- 回复什么
- 是否调用 API

这一层通常与微信版本无关。

### 层 4：发送层

负责：

- 搜索会话
- 粘贴发送
- 截图或回读验证

受影响时，只修 UI 自动化逻辑。

这样的好处是：

- 微信升级时不会“整套重写”
- 通常只会坏掉其中一层
- 便于快速定位问题

## 9. 当前方案的边界

这套方案当前更适合：

- 单账号本地自动回复
- 单会话或少量重点会话自动化
- 本地业务辅助
- 原型验证和轻量生产使用

当前还不适合直接当成：

- 零维护 SaaS
- 纯云端机器人
- 完全无人工监管的大规模营销系统

因为它仍然依赖：

- 本地设备在线
- 微信账号在线
- 本地数据库持续更新
- 微信 UI 没有发生大变化

## 10. 推荐的产品化路径

如果未来真的要给别人用，建议分三步走：

### 第一步：本地单机稳定版

目标：

- 稳定监听一个或几个联系人
- 稳定自动回复
- 有日志和异常恢复

### 第二步：本地代理 + API

目标：

- 回复生成改成 API
- 增加规则配置、白名单、冷却、关键词触发
- 支持人工接管和风险开关

### 第三步：桌面化 / 安装包化

目标：

- 别人不用看源码
- 只需要安装、登录、授权、配置即可使用

最终产品形态更像：

- 一个本地菜单栏应用或后台守护程序
- 一个远程配置和模型 API 服务

而不是“让用户手动跑一堆脚本”。

## 11. 一句话回答几个最常见的问题

### Q1. 自动回复现在是不是靠本地项目在跑？

是。
当前自动回复本质上就是本地脚本在跑。

### Q2. 不打开开发环境行不行？

行。
但必须有本地服务在运行，而且微信本体也要后台在线。

### Q3. 不开微信行不行？

不行。
微信可以在后台，但不能完全退出。

### Q4. 给别人用是不是要走 API？

更准确地说，是“本地代理 + API”。
API 负责智能，本地程序负责收发。

### Q5. 微信更新会不会导致失效？

会有这个风险。
最常见受影响的是抓 key、消息解析、UI 自动化这三层。
